# Implementation Notes

## Goal

Build a cross-platform GitHub Release manager. The user provides an `owner/repo` string or a GitHub URL, the tool reads the latest release, selects the right asset for the current platform and CPU architecture, builds an install plan, executes supported installs, and stores the result in a local manifest.

## Architecture

The repository uses a Rust workspace for the shared core and CLI. The Tauri desktop crate is built separately so a clean clone does not depend on frontend `dist` artifacts during workspace-level checks.

- `crates/core`: shared business rules used by both the CLI and the GUI.
- `crates/cli`: command-line entry point for argument parsing and output.
- `apps/desktop`: Tauri 2 + React desktop manager.
- `README.md` is the English GitHub landing page, and `README_zh-CN.md` is the Simplified Chinese peer. Both files keep a language switcher at the top and describe only implemented behavior.

Core modules:

- `repo`: parse `owner/repo` strings and GitHub URLs.
- `release`: release data models and latest-release client logic.
- `asset_matcher`: deterministic asset scoring with managed-local formats preferred over system installers.
- `install_plan`: turn a release and matching asset into a confirmation-ready install plan, including whether the asset is managed locally, handled by a system package manager, or executed as an external installer.
- `config`: runtime configuration for the GitHub token, proxy, UI language, theme mode, install root, and download acceleration.
- `manifest`: JSON manifest read and write support. Writes use a sidecar file lock so CLI and desktop processes serialize read-modify-write transactions instead of overwriting each other. Manifest and managed-transaction journals are replaced atomically from unique same-directory temporary files opened with exclusive creation; files are synced before replacement and the parent directory is synced on Unix. The rename is the logical commit point: a later parent-directory sync failure is reported as a durability warning instead of a failed save, preventing callers from reversing file moves after the new manifest is already visible. This warning means a sudden power loss could still lose the directory entry. Managed file moves use the sidecar journal so the next operation can restore the before state or finalize the committed after state following a process interruption. System installer records keep both the current install target and, when discovered, the original installer package path so the desktop can open either one without guessing.
- `installer`: download assets, verify or record SHA-256 before extraction or execution, unpack archives and AppImage files, write manifests, and uninstall local installs. Release asset downloads write to a sibling `.part` file first, resume that partial file with HTTP Range when possible, and retry temporary network or 5xx failures before finalizing the cache file. Large downloads can use multiple HTTP Range connections when the server supports byte ranges; unsupported servers, failed range probes, failed segment requests, and small assets fall back to the single-connection `.part` resume path. Managed AppImage installs create a basic desktop entry under the managed root and rewrite or remove it during update, rollback, and uninstall after the manifest transaction has reached its commit boundary, so a manifest write failure does not leave a new desktop entry behind. Managed-local updates stage the new file or directory before replacing the previous contents, so a failed replacement can restore the old install. Managed update, rollback, and uninstall file moves stay under the manifest transaction lock. Recovery accepts only the exact repository-owned move sequence for the recorded operation, including ReleaseDock staging and tombstone names. The persisted managed root is the trust boundary: active installs and rollback snapshots must be canonical direct children of their repository-specific directories, and symlink escapes are rejected before garbage collection, moves, or deletion. Legacy records without a managed root derive it strictly from their managed install path; a successful update persists the derived root. Legacy Windows records that misclassified a bare `.exe` as an external installer may migrate to managed local executable installs only when neither the old nor new asset looks like a setup package and the old record has no adopted launch/install location. Dashboard refresh also repairs existing bare `.exe` records that already live in ReleaseDock's `apps/<owner>-<repo>/` layout so their uninstall action deletes the managed file instead of opening Windows system uninstall settings. Pre-commit tombstones are never garbage-collected, while committed tombstones can be removed by recovery or the next managed operation. Windows system installers are traceable through the ARP/Uninstall registry: when a matching installed entry exposes a real install location or launch target, the manifest records that path and keeps the installer package path separately. Dashboard refresh runs a best-effort adoption pass for Windows system-installer records that still lack a launch target; discovery or save failures keep the existing record visible and must not fail the dashboard refresh. This installer-adoption path is Windows-only after the target manifest record is confirmed to be a system-installer entry, so non-system records keep the same business error on every platform. Linux `.deb` / `.rpm` / `.pkg.tar.*` installs also persist package identity so updates and uninstalls can flow through the system package manager.

## Current Scope

- Release parsing, release note handling, asset matching, manifest persistence, and install plan generation are implemented.
- Manifest format v4 distinguishes managed local installs from system installer records, stores integrity and release-policy metadata, records the trusted root for new managed installs, keeps rollback snapshots, and can store the AppImage desktop entry path. Linux system-package records also keep the package name and manager so the app can remove them without guessing from the cached installer file.
- CLI `install` supports live GitHub requests as well as `--release-fixture` and `--artifact-fixture` for offline testing. `--json` prints only the install plan, and `--yes` skips confirmation prompts. Interactive install and update confirmations summarize the selected install type; bulk updates also summarize how many items are local managed installs, system packages, or external installers.
- CLI `config` reads, updates, and clears the GitHub token, proxy, and install root. `config get` preserves its JSON shape but replaces a saved token value with `***redacted***`. The desktop settings page also exposes language switching and a follow-system/light/dark theme control, defaults to English, and shows the effective install root when no custom path is set.
- CLI `info` shows the latest release note and asset list.
- CLI `doctor` prints config file location, token/proxy state, and the install root without leaking token values.
- CLI `list`, policy-aware `check`, `update`, guarded `rollback`, and `uninstall` support the default manifest path and a `--manifest` override. `check` reports the selected target and its upgrade or downgrade direction. `update` requires exactly one repository target or `--all`; each generated update plan records the selected installed version and release policy so the core rejects a stale plan before reading or downloading an artifact.
- CLI catalog traversal stops on an empty page, rejects repeated page tag sets, and is bounded to 20 pages and 2,000 releases. Fixture-backed non-`--all` listing follows the same first-100 contract.
- New install plans carry an `ExpectedAbsent` selection guard, while update plans carry `ExpectedInstalled` with the selected installed version and release policy. The core validates either state before artifact access and retains its full app-record comparison under the manifest lock before commit. Plans serialized before selection guards were introduced remain readable when the guard field is absent. A new prerelease install also carries its target policy, so the app record, policy, and lifecycle event are committed by one manifest save. Existing app updates retain their saved policy. Rollback guards capture the active version plus the snapshot's absence or identity before confirmation. The core validates that complete state again while holding the manifest lock before moving files, so a snapshot created during confirmation is a stale-plan conflict rather than an implicit rollback target.
- The GUI reads the real manifest and refreshes live GitHub release data. It uses a three-pane workbench layout, shows the important decisions directly, renders release notes with headings, lists, tables, quotes, links, and inline code, streams dashboard refresh progress item by item, keeps dashboard refresh state separate from install/uninstall progress, keeps task progress in the bottom status bar with visible motion for indeterminate work, and localizes those task/status strings with the selected UI language. The inspector keeps the default view focused on release choice, install path, package metadata, and compact recent lifecycle history when the manifest has history for that repo, while omitting low-value management labels from the normal view. Lifecycle history is retained per repo with a small bounded tail so the manifest stays readable while still supporting troubleshooting. It also supports a compact four-state local filter set and a selection danger action with a localized selection summary; that action removes only uninstalled tracked items, while a single selected installed item opens the normal uninstall confirmation instead. Mixed installed/uninstalled selections are disabled instead of combining uninstall and remove tracking. GitHub API requests keep a short timeout, while asset downloads use a separate idle timeout so large files do not fail just because the total transfer takes longer than the preview budget.
- The desktop inspector collects the first 100 non-draft release versions across bounded GitHub pages, starts with a compact state summary, and then exposes a unified decision panel with state-specific emphasis. Uninstalled repos emphasize target-version selection and the centered `Preview install` action, with asset and install-path rows separated as confirmation details. Installed repos emphasize the current installed version and status pill in the panel header, keep target-version selection as a lower-weight policy control, and isolate uninstall in its own danger area. The selected target version and published time stay in the top summary line above that panel, and the panel itself does not repeat a separate release-info card or expose a stable/prerelease channel control. Asset and install-path rows expose a copy button with localized feedback, keep the full value in hover text, and clip long values so the inspector width stays stable. The version selector marks release-list loading with a subtle style state, and action buttons provide pressed feedback without changing layout. The frontend derives the internal preview channel from the selected release's prerelease flag before calling Tauri, and it suppresses the secondary install-location action when that same location is already the primary action. Version selection, release direction, checksum discovery, and policy eligibility remain core decisions; dashboard selection also follows a pin beyond page one. When a selected repo is already in a failed install state, the version strategy block hides its preview button so the retry action stays singular. For newly tracked repos with an installable asset, the inspector also hides the redundant top-level install button so the install preview becomes the primary call to action. Installed app inspectors no longer expose a secondary `Open release` button, do not use Release as a fallback primary action, and do not expose a manual system-install re-detect action; no-installable tracked repos still keep `Open release` as the primary action. Install confirmation returns the complete path-free preview identity. The Tauri backend validates its manifest guard before network or artifact work, rebuilds the release, asset, integrity, and install plan, and rejects changes to any execution-relevant field before using the server-owned plan. Rollback confirmation similarly compares the previewed active version and snapshot identity with the current manifest, then creates the core rollback guard from that trusted state. Frontend-provided download, install, or snapshot paths are never used for filesystem operations.
- Uninstall flows now require an explicit confirmation card before they run. The desktop exposes one `Uninstall` entry for installed records, then branches after confirmation: managed-path uninstall deletes ReleaseDock's managed directory and rollback snapshot, Linux package uninstall delegates to the recorded package manager and clears the manifest record, and Windows system-installer uninstall opens the OS uninstall tool without deleting system files or removing the manifest record automatically. After opening the OS tool, the task status tells the user to finish the uninstall there and refresh ReleaseDock.
- The GUI now also exposes a launch target for managed installs when one can be inferred, so the detail inspector can open the software itself in addition to the install location. AppImage installs use the installed file directly; archive installs infer a launchable executable from the extracted tree when possible. Installed apps keep a secondary install-location action when the primary action is opening the app. System installer records that have not been adopted yet keep two package-oriented actions: running the installer package file itself and opening the folder that contains that package. When Windows ARP discovery finds a real installed app path, the primary action switches to opening the app, the secondary install-location action opens the real installed directory, and the installer package path remains a separate detail row instead of a default secondary folder action.
- For repos with no installable asset on the current platform, the inspector keeps `Open release` as the main action and can show a small non-managed install guidance card when the release title or notes mention Docker or source compilation. The guidance is intentionally shallow: it only inspects the release title and note text, so the UI does not need any extra repository-file fetches before giving the user a next step. The install preview uses a compact version-plus-asset summary, keeps asset file and install path as the main confirmation rows, and folds integrity plus permission warnings into one safety note. Its visual treatment keeps the body neutral, uses teal only for asset/type identity, and keeps amber local to the warning and confirmation affordances.
- Asset selection prefers managed-local formats first, including Linux executables without an extension when they clearly match the current platform and architecture, then Windows setup/MSI or other system installers as fallback assets. Windows bare `.exe` builds that are not installer-like stay managed locally so future update and uninstall flows remain inside ReleaseDock whenever a portable or directly runnable release artifact exists.
- Linux system packages record the package name and manager in the manifest so the app can refresh, uninstall, and display system-managed records without guessing from the cached installer file. The package inspect, install, and remove commands are generated from a single manager-specific command spec for Debian, RPM, and Pacman packages.
- Tagged Windows release builds use CI Authenticode signing when signing secrets are configured. `WINDOWS_CODESIGN_PFX_BASE64` stores the base64-encoded PFX and `WINDOWS_CODESIGN_PASSWORD` stores its password; the workflow imports the certificate only for the tag job, passes the thumbprint to Tauri packaging, and verifies the standalone executable plus NSIS/MSI bundles with `signtool`. When both secrets are absent, the release continues with unsigned Windows artifacts and an explicit CI warning.
- Install and uninstall success paths keep the task context alive until the finished or failed state is visible, so the UI does not depend on the final event delivery alone and the bottom bar can show the terminal frame reliably.
- Successful installs clear the downloaded cache copy after the managed install finishes, while failed installs leave the download cache or `.part` file in place for retry or diagnosis.
- Desktop settings are auto-saved after editing GitHub token, GitHub proxy, language, install root, download acceleration, or related local values. Download acceleration's maximum connection field preserves an in-progress edit and clamps to the supported 1-8 range on blur or save. The proxy value is used for GitHub API queries and Release asset downloads, with UI examples using anonymized formats such as `http://proxy.example.com:port`. The settings sidebar keeps only a network configuration card with Token/proxy state, the proxy format hint, and a GitHub connection test that uses the current draft proxy and optional token values without requiring a save first. After the app loads the saved settings, it also starts one non-blocking GitHub API reachability check for that Token/proxy combination; the dashboard continues loading independently. The install root field now shows the resolved default directory until a custom path is entered.
- Repositories without a published release render as a neutral `No release` state instead of a failure, and the seeded `releasedock` tracking entry can still be removed from the list.
- The install root is the local workspace base directory. Download caches go under `downloads/`, and managed installs go under `apps/<owner>-<repo>`. The settings page label "install root" refers to this base directory.
- GUI filtering only applies to the local managed list. It does not search GitHub globally. Public repositories do not require a token, while private repositories and frequent refreshes should use one.
- The desktop top bar does not warn merely because the GitHub token is empty. Public repositories can work without a token. Network/proxy failures point users to the GitHub proxy, while confirmed rate-limit or authentication failures point users to the token. Other GitHub HTTP failures remain generic so a normal 403 response is not misreported as a token problem. The reminder opens Settings and highlights the network fields.
- The installer supports `.tar.xz` archives. Windows `.exe` / `.msi` and Linux `.deb` / `.rpm` assets are marked as requiring user confirmation before installation.
- Desktop icon assets are generated from `apps/desktop/src-tauri/icons/icon-source.svg` into the `icon.png` and `icon.ico` paths referenced by `tauri.conf.json`. The mark should stay readable at tray size and avoid text or letter-only branding.
- The GitHub README pair documents ReleaseDock's boundary against OS package managers, AppImage-focused managers, Android update tools, and one-line installer scripts. It also keeps a short current-limitations section so users understand that ReleaseDock has no app catalog, no published macOS build, no zsync/delta updates, only basic AppImage desktop entry integration, external-installer behavior controlled by upstream installers, and no publisher-identity verification beyond available checksums and recorded SHA-256 digests.
- **System tray + background check**: closing the main window hides it to the system tray instead of quitting the app. The tray icon context menu offers "Check updates", "Open window", and "Quit" entries. The background checker runs once when it starts, then re-checks all tracked and installed repositories at the configured interval (default 30 minutes). Native notifications are only sent when the positive update count changes, while the tray tooltip and top bar use the latest successful count. A failed background pass emits a failed status for diagnostics without clearing the previous successful badge. A successful manual dashboard refresh clears the background badge because the visible list has just been refreshed. The settings page exposes a "background check" toggle and an interval field. The feature is enabled by default.
