# Windows UI

## Design Goal

The Windows first screen is a compact workbench, not a welcome page. Keep the most important decisions visible, move explanatory copy into buttons, fields, and hover text, and make it easy to judge which GitHub Release apps need attention before opening release notes or starting a task. The default UI language is English, and the settings page offers an English / Simplified Chinese switch. The bottom status strip and task feedback follow the selected UI language too. The inspector should keep installed-app details focused on the current release, install path, package metadata, and recent lifecycle history when that history is available, while avoiding low-value internal labels in the default view.

## Pages

- Update manager: the default view. Keep the filter and bulk-action tools compact on one toolbar row where space allows, with All, Updates, Action needed, and Failed. Show current and no-release states in the list, but do not surface them as separate filters.
- Update manager layout: keep the list and inspector side by side when both columns can remain readable. At medium widths, compress the inspector rail and table columns first so non-fullscreen windows still preserve the two-column workbench. Only switch to a single column at narrow widths, with the list above the inspector. If the table needs more width, scroll or clip it inside the list card instead of letting it cover the inspector.
- Top bar: keep the page title left-aligned and place configuration status plus page actions in a single right-aligned cluster. The update manager may show the token pill, update-count pill, and Check updates button together; settings should keep the top-right area minimal and surface configuration state in the sidebar instead of pinning a lone token pill beside the title.
- Add GitHub repository: keep the add-repo row in the list workbench header, next to the managed-apps summary. Accept an `owner/repo` string or GitHub URL and add it to the tracked list.
- Empty dashboard: when there are no managed apps yet, collapse the workbench to a single wide panel and prioritize the add-repo input plus the no-apps hint. Do not reserve a right-hand inspector column for the empty state.
- Local records: if the tracked-repository store is corrupt, the dashboard still keeps manifest-backed installed app records visible. Strict add, remove, and bulk-remove operations continue to report the tracking-store error instead of overwriting the corrupt file.
- Filter tracked software: filter the local list only; do not search GitHub globally.
- Bulk actions: support row selection, compact select-all/clear controls, and a short selection summary beside the destructive action. A single selected installed app changes the danger action to `Uninstall` and opens the same uninstall confirmation used by the inspector. Uninstalled tracked items keep `Remove`; mixed installed/uninstalled selections are disabled so uninstall and remove-tracking semantics are not combined in one click. Busy state disables this selection action with the normal task-running reason.
- Settings: GitHub token, install root, GitHub proxy, language, theme, background checks, start-with-Windows, notification permission state, and download acceleration. Changes are saved automatically after editing, and the install root field shows the resolved default directory until the user overrides it. If start-with-Windows cannot be changed, the status strip should name that failure instead of reporting a generic save problem. The language and theme choices should use button groups, not labels that wrap clickable controls, so clicking empty space does not toggle the first option. The theme setting offers follow-system, light, and dark modes and only targets the desktop window. Download acceleration uses a toggle plus a bounded connection-count input. The proxy field should name the GitHub scope clearly, explain that it affects GitHub queries and Release asset downloads, and show an anonymized format example such as `http://proxy.example.com:port` instead of a real address. On wide windows, use a left editing column and a compact right network configuration card only; collapse to one column on narrow windows. Put the GitHub connection test in that network card. On first open, show manifest and tracked-repository records from the local-only dashboard, then run one GitHub reachability check. Start release and version requests only after a successful check; network, proxy, rate-limit, and Token failures keep those local records visible and expose the existing warning, settings, and retry actions. A failed version-list request keeps the current target selection visible and shows retry plus network-settings actions in the inspector. This prevents a broken network path from leaving the release list in an endless loading state.
- GitHub token: optional for public repositories; recommended for private repositories and frequent refreshes.
- Config warning: do not warn merely because the GitHub token is empty. Public repositories can work without a token. Show a top-bar warning only after the startup check, manual connection test, or another GitHub request identifies a concrete problem: network/proxy failures should point to the GitHub proxy, while rate-limit or authentication failures should point to the token. A generic GitHub response that is not a rate limit or auth error should ask the user to retry or inspect the details instead of guessing. Clicking the warning should open Settings and briefly highlight the relevant network fields instead of showing a modal.
- Sidebar footer: show the product name and subtitle only. Do not use the lower-left area as a repository shortcut.
- Copy strategy: show data and state directly, keep button and field explanations in hover text, render release notes with simple Markdown structure, skip generated HTML comment anchors, and display asset and install path directly. The release note view should be larger than the metadata blocks and should separate headings, lists, tables, quotes, inline code, links, and body text.
- Hover placement: icon button help text should open to the right by default and flip left near the right edge, so the tooltip does not cover the relevant panel.
- Install locations: the detail panel should expose open-folder actions, and settings should expose open-root and restore-default actions. Managed installs should open the containing folder. System installers that have not been adopted yet should distinguish the installer file from its folder: the primary action runs the installer package itself, while the secondary folder action opens the installer package directory. ReleaseDock automatically attempts Windows registry adoption after installer runs and during dashboard refresh; the inspector also offers a compact `Re-detect install` action for installed external-installer records that still have no adopted launch target. Once it has adopted the real installed app location, the secondary folder action switches to the installed app directory and the installer package directory is no longer emphasized.
- Managed installs should also expose an open-app action when a launch target can be resolved. AppImage entries can launch directly; archive entries should try an inferred executable first and fall back to opening the install location if no launch target is available. Bare Linux `Executable` entries are treated as managed local installs without a GUI launch target, so they fall back to opening the install location instead of offering a launch action, and they keep ReleaseDock-managed uninstall behavior even for legacy records. Bare Windows `.exe` records that already live in ReleaseDock's managed `apps/<owner>-<repo>/` layout should likewise stay on the managed uninstall path instead of opening Windows system uninstall settings. In the inspector, the secondary open-app button should only appear for update-available managed installs so the primary action does not repeat itself, and the secondary actions should use a compact two-column layout instead of a long vertical stack.
- Tracked repositories with no installable asset for the current platform should show `Open release` as the primary action instead of `Install`, so the user can inspect the release page without triggering an install preview.
- Installed app inspectors should not show a secondary `Open release` button or use Release as a primary-action fallback. If an installed record has no launch target and no usable install or installer path, show a disabled primary action with a concrete reason. Release links can remain in details and non-managed guidance, and tracked repositories with no installable asset still use `Open release` as the primary action.
- When a tracked repo has no installable asset and the release title or notes mention Docker or source compilation, the inspector should show a small non-managed install guidance card that points the user back to the release page instead of pretending there is a one-click install path. Keep that guidance scoped to the release title and notes; do not scan repository files before showing it.
- Install preview: once the preview opens, keep only `Cancel` and `Confirm install` in the action area. Lead with a compact version-plus-asset summary, then show only install-critical rows such as asset file, install path, and package manager when present. Integrity status, checksum source, and system-permission confirmation belong in one lightweight warning strip instead of separate metadata rows or repeated bullet notes. Keep the preview body mostly neutral, use teal for the asset/type badge, and reserve amber for the warning strip and confirm action. In dark theme, the preview panel, value rows, copy affordances, select controls, lifecycle decision cards, history entries, and Release note nested content must stay on dark surfaces instead of carrying light input backgrounds or white gradients into the inspector. Mark the panel as an alert dialog and move focus to its confirmation button.
- Release lifecycle: the inspector starts with a compact state summary, then shows a unified decision panel with the selected release title and the first 100 non-draft releases collected across bounded pages. The selected target version and its published time stay in the top summary line above that panel, and the panel itself no longer repeats a separate release-info card or stable/prerelease channel control. For uninstalled repos, the target-version selector and centered `Preview install` action form one compact decision row, followed by lightweight asset and install-path rows with enough spacing to read as confirmation details. For installed repos, the panel header emphasizes the current installed version and a small state pill such as `Latest` or `Updates`; target-version selection sits in a quiet nested control surface, and uninstall is isolated in a shallow red danger area at the bottom. Asset and install-path values should include a small copy affordance, use hover text for the full value, and keep long text clipped rather than resizing the panel. While versions are loading, the selector gets a subtle loading border without moving adjacent controls. When the current repo is already in a failed install state, the version strategy block suppresses its preview button so the retry action stays singular. The confirmation panel shows the target version, upgrade/downgrade direction, integrity status, and checksum source. The UI returns the complete path-free preview identity to Tauri but never supplies repository/download URLs or install paths. A late response is discarded unless its request and repository still match the current inspector.
- Rollback: show the action only for a managed install with a recorded snapshot. Its alert-dialog confirmation names the active and snapshot versions and focuses the confirmation button. System-package and external-installer records do not show rollback. A late response cannot cross repositories, and confirmation requires the preview repository to match the selected repository before the frontend-provided snapshot identity is validated against the current manifest.
- Right-side actions: keep the inspector commands visually layered inside the decision panel, with a filled primary action, lighter secondary actions, and a single restrained `Uninstall` danger action at the bottom only after the selected software is installed. Managed files, Linux packages, and Windows system-installer records all use that same entry and then branch after confirmation. The right side no longer exposes separate `Use system uninstall` or `Remove tracking` buttons; remove tracking stays on the left list controls. Do not render the same install-location action both as a primary action and as a secondary action. The install preview confirmation button should stay in the amber confirmation palette instead of reusing the regular green primary style.
- The inspector should label the asset row as `No installable asset for this platform` when the repository has no matched asset for the current OS.
- The inspector should not keep an empty secondary-action row after hiding duplicate actions, and the asset file plus install path rows should span the full inspector width so long names and paths stay readable. For newly tracked repos with an installable asset, the version preview should act as the main call to action instead of showing an extra primary install button beside it.
- The list row action column is clickable. For `needsChoice` items it launches the same install-preview flow as the inspector `Preview install` button, so the user can start installation from the table instead of hunting for the right-side control.
- For `needsChoice` items, the inspector should bring the action controls above release metadata and release notes so the install decision is visible before explanatory content.
- System installers: Windows `.exe` / `.msi` and Linux `.deb` / `.rpm` files require explicit confirmation and must not be treated like one-click installs. Successful installs should clean up the temporary download cache copy.
- System tray: closing the main window minimizes the app to the system tray instead of quitting. The tray menu provides "Check updates", "Open window", and "Quit" actions. Left-clicking the tray icon, choosing "Open window", and re-launching the desktop executable while ReleaseDock is already running must all restore, unminimize, and focus the same existing window instead of starting another background process. The desktop remembers the previous window size and position. If start-with-Windows is enabled, the app starts with a background argument, skips dashboard and GitHub requests while hidden, and initializes the workspace only when the tray or a second launch restores the window. The tray tooltip shows the pending update count ("ReleaseDock · 3 updates available") when there are new releases, or just "ReleaseDock" when everything is current.
- Windows desktop release builds should run as GUI subsystem binaries, so launching the app normally must not leave a console window behind. Windows shell-open actions should use the system shell rather than `cmd`.
- Download acceleration: large Release asset downloads use multiple HTTP Range connections only when the server reports range support. The settings page exposes a toggle and a maximum connection count field, defaulting to enabled with four connections. The connection field keeps the user's in-progress edit and clamps to 1-8 on blur or save. Small assets, disabled acceleration, servers that ignore Range, failed range probes, and failed segment requests fall back to the single-connection `.part` resume path.
- Background check: the checker waits for the configured interval before its first request, then re-checks all tracked and installed repositories for new releases at that interval. The settings page exposes a toggle ("Background check") and interval field ("Check interval" in minutes). The feature is enabled by default with a 30-minute interval. Native notifications are deduplicated by positive update count, so the same pending count does not alert repeatedly. Network, proxy, rate-limit, authentication, and other per-repository failures are counted instead of being treated as "no update". A partial or failed pass keeps the previous successful badge, suppresses incomplete notifications, and shows a localized status action that opens network settings; a complete pass updates the badge and tooltip. The settings page shows the current OS notification permission state, offers an explicit permission request before the OS blocks notifications, and opens Windows notification settings after notifications are blocked. Blocked native notifications still leave the tray tooltip and top-bar count available. The top bar shows an "N updates available" pill from the latest successful background pass until a successful manual dashboard refresh clears it.

## Visuals

- Background: `#F5F7FA`
- Panels: `#FFFFFF`
- Primary: `#0F766E`
- Confirmation: `#B45309`
- Failure: `#B91C1C`
- Font: `Segoe UI`
- Version, path, and asset labels: `Cascadia Mono`

The application icon should use the ReleaseDock dock-and-download mark from `apps/desktop/src-tauri/icons/icon-source.svg`, generated into the Tauri `icon.png` and `icon.ico` bundle assets. The icon must remain legible without letters at 16px tray size and 256px installer size.

The layout should feel like a desktop operations tool, using a table and a detail inspector instead of a marketing-style card grid. The add-repo control, list summary, search, filters, and bulk actions should read as one workbench rather than separate cards.
The right-hand inspector needs enough width for long asset names and install paths. Task progress belongs in a compact bottom status bar so downloads, installs, and uninstalls stay visible without displacing release notes; optional banners above the content must not make that status bar occupy the main content row. Idle status uses a single compact row, while checking, download, install, uninstall, and failed task states may expand to show a progress track. Indeterminate work should keep moving instead of freezing on a static bar. Determinate download and install progress should fill from left to right at the reported percentage without a sliding animation, and the percentage label should stay fully visible. When an interrupted asset download resumes from a `.part` file, the progress bar should start from the already downloaded byte count instead of visually restarting from zero. Dashboard refresh should stream item updates so the list can paint progressively instead of waiting for the full request to finish, and that refresh state should not overwrite install or uninstall progress. Zero-percent work should still show a visible sliver of progress, and failures should stay readable in the same strip. Repos without a published release should show a neutral state, not a failure. Release note tables should scroll horizontally instead of collapsing into unreadable text. The settings form should stay compact, with the install root presented as a standard row rather than a highlighted card, and the first screen should avoid repeated page titles or tall tool blocks that push the list too far down.
The right-hand inspector should keep release note summary and version information visible without making the first screen too dense. The release note block should be visually dominant and capable of handling headings, paragraphs, lists, and code blocks. Install preview requests should fail within the shared GitHub timeout budget so the bottom status strip can leave the processing state on its own instead of hanging forever. If an install fails, keep the preview open and relabel the confirmation action as retry install so the user can immediately try again. The bottom status strip keeps the task description, percentage chip, and progress bar on separate lanes so the percentage stays readable while the fill still runs edge to edge.
Buttons should provide light pressed feedback without shifting layout. Copy and disabled-action explanations belong in native hover text so the main inspector stays compact.
